# Area E2: Studio panels (`packages/web/src/areas/studio/panels/`)

As of: HEAD `5f41cd8a`. A path without a prefix starts at `packages/web/src/areas/studio/`.

## Findings

### E2-1: A manual path keeps a hidden guard that acts at runtime

- Case:
  - On the step page, the author sets "triggered by: a condition" for the path `approve`. She builds the row `amount > 1000`. The draft stores `guard: {lang:"cel", src:"data.amount > 1000.0"}`. Then she picks "a participant's choice".
  - The call `updatePath(index, { trigger: "manual" })` sets only `trigger`. The keys `guard` and `priority` stay in the draft. The step page hides the guard row for a manual path. It offers no editor and no remove control for the guard any more.
  - At runtime, `resolveAvailablePaths` filters manual paths by their guard. An instance with `amount = 5` does not get the button "approve". A direct submit ends in `GuardRefused`.
  - The canvas also draws the guard only on automatic paths. The form preview shows the button with no condition.
- Location: `panels/PathsPanel.tsx:284-303` (trigger switch), `:306-329` (guard only for `automatic`); `src/runtime/fields.ts:292-296`; `src/engine/transition.ts:538-543`; `canvas/CanvasView.tsx:1502-1510`; `panels/FormPreview.tsx:155-161`
- Severity: high
- Evidence: confirmed. Read: PathsPanel in full, `list-ops.ts::updateAt` (shallow merge), the runtime and engine sites above, the canvas path label.
- Counter-evidence sought:
  - The Paths tab (`pathRows.ts:63`) and the Changes tab show `guardSrc` for every trigger. There the guard is visible, but read-only. No check reports a guard on a manual path. The check `checkPathTriggerConsistency` (`src/schema/definition.ts:884-908`) inspects automatic paths only.
  <!-- antislop: allow negation-habit -->
  <!-- "carries no guard" is a verbatim quote of the studio-condition-builder spec. -->
  - No other writer sets `trigger`: `git grep` shows only `PathsPanel.tsx:288` and `:300`. The specs contradict each other. The spec `studio-app/spec.md:1257-1259` says "A manual path can carry one". The spec `studio-condition-builder/spec.md:416-417` says "since a manual path carries no guard". The finding survives the search.
- Known: new
- Suggestion: Show the guard editor for both triggers, as `studio-app` requires. Alternatively, ask on the switch to `manual` and remove `guard`/`priority`. Resolve the spec contradiction in an OpenSpec change (`studio-condition-builder`).

### E2-2: The `instance.query` form writes every comparison value as a string

- Case:
  - The author builds an `instance.query` data source with the row `where: priority (number) eq 1`. The literal field writes `value: "1"`. At runtime this becomes `body->'data' @> {"field_prio":"1"}`. Instance data holds the number `1`, so nothing matches. The participant sees an empty select field. With `ne`, by contrast, every instance matches.
  - The same holds for a boolean comparison: `"true"` instead of `true`. If the author picks the operator `in`, the same field again writes a string. The config schema requires a non-empty list, though. This config fails only at publish.
- Location: `panels/shared/InstanceQueryForm.tsx:224-228` (operator, including `in`), `:249-254` (literal always `e.target.value`); `src/runtime/queries.ts:318-326`; `src/engine/instance-query-source.ts:21-44`
- Severity: high
- Evidence: confirmed. Read: InstanceQueryForm in full, the SQL compilation, the config schema and the publish checks.
- Counter-evidence sought:
  - The config schema admits `z.string()` for every field (`instance-query-source.ts:21`). The check `validateInstanceQueryReferences` inspects the compared field only for "non-scalar". It ignores the type of the literal (`src/engine/definitions.ts:318-332`).
  - The type `TargetRef` has no type field (`useTargetProcessCatalog.ts:5-9`). So the form does not know the field type at all. The studio check for registry configs always stands at "not-run" (`draft/validation.ts:79-80`). For `eq`/`ne` no check reports anything. For `in`, only the publish reports it. The finding survives the search.
- Known: new
- Suggestion: Add the field type to `TargetRef` and parse the literal by it (number, boolean). For `in`, show a list input and disable `valueFromField`.

### E2-6: "+ Add row" on diverging visibility overrides removes all overrides

- Case:
  - The field `cost_center` sits in step A with `visible: false` and in step B with `visible: data.x == "a"`. The row "Only ask this when" shows "These steps currently disagree" and "This replaces a literal condition on: A". The author presses only "+ Add row".

  - Afterwards the field is visible in A and B with no condition, before the author enters any value. If the author removes the row again, the overrides do not come back. The studio has no undo.
- Location: `panels/FieldCatalogPanel.tsx:725-728`, `:997-1001`; `panels/shared/ConditionInput.tsx:147-152`; `panels/shared/ConditionBuilder.tsx:150-153`; `draft/field-usage.ts:99-107`
- Severity: medium
- Evidence: confirmed by reading the whole chain.

- Known: new

### E2-7: A label change renames the field key without updating the CEL readers

- Case:
  - The published field "Amount" has the key `amount`, the value derived from the label. A guard reads `data.amount > 1000.0`. The author changes the base label to "Total amount". The function `nextFieldKey` treats the key as "live", because it matches the previous derivation. It writes `key: total_amount`.
  - No code rewrites the readers. They are guards, `visible`/`required`/`readonly` expressions and `validation.rule`, including the field's own "this answer" rule. They also include the timer `deadline` and mapping values.
  - The checks report unknown variables without naming the rename. Mapping values in plugin configs stay unchecked (FIELDS-17). If another field later gets the key `amount`, the old expressions silently rebind (FIELDS-18).
  - The same holds for a key field the author types into directly: it writes on every keystroke (`FieldCatalogPanel.tsx:397`). Similarly, a change or removal of an option value leaves every CEL comparison on the old string in place. No type check flags it.
- Location: `panels/FieldCatalogPanel.tsx:701-710`, `:393-398`; `panels/fieldCatalogLogic.ts:23-35`; `draft/deriveKey.ts` (`shouldAutoDeriveKey`)
- Severity: medium
- Evidence: confirmed. The command `git grep` finds no CEL rewrite on a rename. Only the group key rewrites views (`view-group-sync.ts`).
- Counter-evidence sought: The spec `studio-app/spec.md:1399-1426` requires automatic derivation for every field. The archived design `2026-08-24-auto-derive-key-from-label/design.md` accepts that derivation resumes when "the key already reads as label-derived". It does not assess the consequences for CEL. The checks catch the direct break. They miss the later rebinding.
- Known: related to FIELDS-18 (`docs/decisions.md:1205`) and FIELDS-17 (`:1192`). The trigger "label change" is new.
- Suggestion: Disable automatic derivation for a field that already has CEL readers or comes from a published version. Or rewrite the readers on a rename. This needs an OpenSpec change (`studio-app`).

### E2-10: The condition builder does not read back its own output for integer and negative literals

- Case:
  - The field `prioritaet` is `{type:"number", format:"integer"}`. The builder correctly writes `data.prioritaet > 3`. After a remount (page change, reload), cel-js 8.0.0 parses the `3` as `BigInt` (`node_modules/@marcbachmann/cel-js/lib/parser.js:332-341`).
  - The function `literalOf` accepts only `string|number|boolean`. So the row shows raw, as CEL text instead of as a comparison. The canvas label shows CEL instead of plain text.
  - The same holds for `data.amount > -5.0`: a unary minus node `-_` also turns into a raw row. The rule builder uses the same functions. In addition, `celLiteral(1e21, "double")` yields `"1e+21.0"`, and that is not valid CEL.
- Location: `panels/shared/conditionLogic.ts:251-255`, `:288-292`, `:343-347`; `panels/shared/ruleLogic.ts:109-117`
- Severity: medium (it affects every condition on an integer field. It violates the no-code goal but loses no data)
- Evidence: confirmed. Read: the parser (`readNumber`, `#consumeLiteral`, `ASTNode`) and the operators (`'-_'`). The test `studio-conditionLogic.test.ts:142-151` checks only the write. It skips the read-back.
- Counter-evidence sought: The search found none. The function `parseAst` passes the AST through unchanged (`src/cel/check.ts:532-538`).
- Known: new
- Suggestion: The function `literalOf` accepts `bigint` (as `Number`, while safe) and folds `-_` over a number value. Add a round-trip test per type.

### E2-11: Hidden tabs recompute everything on every keystroke (the ponytail ceiling arrives earlier)

- Case:
  - All eleven tab bodies stay mounted, and `hidden` only hides them. The author types a label in the Fields tab. Every mutation also redraws `FieldMatrixGrid`. That redraw reruns `writtenFieldCounts(draft)`, which builds dominator sets over the step graph.
  - Each row and column calls `eligibleTargetEntries` up to nine times for the bulk badges. Each call walks all targets, `cellEntry` (`findIndex`) and `gatedKeys`. The latter calls the `written` accessor. The accessor walks all steps and their view entries on every call, with no cache.
  - Likewise, `ChangesView` runs `describeChanges` on every keystroke through `useMemo([state, draft])`. That means JSON copies of both bodies plus a diff. Afterwards `ChangeList` redraws all rows, including the Developer view JSON.
  - The ponytail comment sets the ceiling only at "hundreds of rows after an import". Here every keystroke on every tab pays the price.
- Location: `screens/EditScreen.tsx:810-817`, `:992`; `panels/FieldMatrixGrid.tsx:438-446`, `:511`, `:682`, `:727`, `:774`, `:804`; `draft/view-flags.ts:109-167`; `panels/ChangesView.tsx:124-127`; `panels/ChangeList.tsx:350-353`
- Severity: medium
- Evidence: assumed for the size. Reading confirmed the mechanism. A measurement of the commit time is missing, see the repro proposals.
- Counter-evidence sought: The grid `FieldMatrixGrid` memoizes `rows`, `written` and `technicalIds`. All of them depend on `draft`, so they rerun on every keystroke. The panel `FieldMatrixPanel` mounts the grid unconditionally (`:157`).
- Known: FIELDS-14 (`docs/decisions.md:1158`) covers only the Fields tab. The studio canvas class PERF-3 comes from the review of 2026-07-29. Matrix and Changes are new.
- Suggestion: Tie the costly derivation to the visibility of the tab, the way `FieldsTab` already receives `visible`. Or use `useDeferredValue(draft)`. Cache the `written` accessor per `(fieldId, step)`.
