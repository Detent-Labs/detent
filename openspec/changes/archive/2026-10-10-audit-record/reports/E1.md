### E1-1: `KNOWN_KEYS` lacks `collaboration`, so the JSON surface then refuses every Apply
- Case:
  - An author opens a draft and opens the header bar's `⋮` menu. The author
    clears the "Comments" checkbox.
  - The code at `ProcessHeaderBar.tsx:969-970` writes
    `d.collaboration ??= {}; d.collaboration.comments = false` into the draft.
  - Then the author opens the JSON surface from the same menu. The author
    changes `"label"` and presses Apply.
  - The function `JsonView.apply` (`panels/JsonView.tsx:51-58`) calls
    `parseDraftText` (`panels/draftJsonLogic.ts:24-27`). That function calls
    `checkDraftShape`.
  - The key `collaboration` is missing from `KNOWN_KEYS` (`draft/load-guard.ts:19`).
    So the check returns
    `collaboration: unrecognized top-level field 'collaboration' — this may not be a process body`.
    Apply refuses.
  - This holds for every draft that carries `collaboration` at process level,
    whatever the author changes.
  - Per `CLAUDE.md`, the JSON surface is the escape hatch for everything no
    builder expresses. Here it is locked completely. The message also claims
    that the text is no process body.
- Mechanism:
  - The schema `processBody` declares eleven keys, among them `collaboration`
    (`src/schema/definition.ts:974-992`, the field on line 990).
  - The list `KNOWN_KEYS` names ten. Every key outside that set becomes a guard
    error (`load-guard.ts:33-35`). The function `parseDraftText` turns every
    error into an abort.
  - A comparison of the other mirrors: `PROPERTY_WORDS` and `OWNED_LISTS`
    (`draft/changeSet.ts:64-161`) cover all keys of `processBody` and `step`.
  - The file `sectionsFor.ts:13-35` covers all step keys (see "Checked without
    a finding"). Only `KNOWN_KEYS` is stale.
- Location: `packages/web/src/areas/studio/draft/load-guard.ts:19`;
  `packages/web/src/areas/studio/panels/draftJsonLogic.ts:24-27`
- Severity: high
- Evidence: confirmed (read: `load-guard.ts:1-63`, `draftJsonLogic.ts:1-34`,
  `JsonView.tsx:1-81`, `definition.ts:910-992`, write sites
  `ProcessHeaderBar.tsx:966-985`).
- Counter-evidence sought:
  - (1) A normalizer before Apply: `draft/types.ts` is a generic
    `DraftOf<AuthoredProcessBody>`, with no filter. The function
    `formatDraftText` is plain `JSON.stringify` (`draftJsonLogic.ts:32-34`).
  - (2) A test against the schema: `packages/web/test/studio-load-guard.test.ts:31-44`
    checks a fixed object without `allowedGroups`, `cancellable` and
    `collaboration`. The module does not export `KNOWN_KEYS`, so no test can
    hold it against `processBody.shape`.
  - (3) The file `docs/decisions.md` has no match for `KNOWN_KEYS` or
    `load-guard`.
  - The finding stands.
- Known: new (the rule itself stands in `CLAUDE.md` under Conventions,
  "A new `ProcessBody` or `Step` field has hand-kept mirrors")
- Suggestion: Add `"collaboration"` to `KNOWN_KEYS` and add
  `expectObject("collaboration")`. Export `KNOWN_KEYS` and compare it in the
  test against `Object.keys(processBody.shape)`. Zod 4 keeps `.shape` on the
  refined object, and `studio-changeSet.test.ts:925-931` already uses that.
